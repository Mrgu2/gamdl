# 艺术家下载需求整理

## 1. 目标

把用户提出的“支持按艺术家下载”整理成一个可讨论、可排期的功能需求，而不是停留在口头反馈。

## 2. 已确认事实

### 用户反馈

- 当前版本整体使用体验顺滑。
- 解密后的 `ALAC` 文件放到 `ZX300A` 上可以正常播放。
- 歌词滚动表现正常。
- 用户希望进一步支持“按艺术家下载”。

### 从当前仓库验证到的现状

- 桌面版 README 目前只把“歌曲、专辑、歌单下载”列为正式支持范围。
- CLI / 底层下载逻辑已经存在 artist 相关能力。
- Web GUI 当前会把 `artist` 识别出来，但明确标记为不支持类型。

结论：这更像是“把底层已有能力在桌面产品里正式暴露并补完交互”，不是从零实现整个下载链路。

## 3. 截图分块整理

### 分块 A：仓库入口与使用反馈

这部分主要是在确认仓库地址、能否找到项目以及基本使用情况。

可提炼信息：

- 用户已经实际下载并使用过当前工具。
- 当前讨论不是“能不能用”，而是在“能用之后还缺什么”。

### 分块 B：安装 / 环境兼容诉求

这部分提到了 Docker 与 wrapper 的使用问题。

可提炼需求：

- 文档里的 Docker 命令建议补充 `--platform linux/amd64`，至少在说明步骤 4 和 5 里给出兼容提示，减少 Apple Silicon / Rosetta 相关报错。

可提炼问题现象：

- wrapper 构建过程容易报错。
- 部分用户会遇到 Rosetta、代理、源码目录缺失等环境问题。

### 分块 C：下载失败后的补救诉求

这部分是截图里最明确的功能请求之一。

可提炼需求：

- 下载结束后，针对失败歌曲提供“重试失败歌曲”入口。
- 用户不希望为了补一两首漏下的歌，再手动回去重新找原始导入链接。

可提炼隐含目标：

- 降低失败任务的补救成本。
- 让批量下载在“尾部修复”阶段更顺手。

### 分块 D：性能 / 稳定性讨论

这部分更多是在描述现状，而不是明确提出新功能。

可提炼信息：

- 当前大批量下载存在一定失败率。
- 失败原因里混有网络波动、服务器限流、解密能力限制等因素。
- “并发能力不好提”是现状判断，不等于当前截图里已经形成明确需求单。

### 分块 E：后续沟通预期

这部分主要是用户表达“有更新请通知”。

可提炼信息：

- 用户对后续版本更新和新功能上线是关注的。
- 这更像运营 / 发布沟通预期，不是本次核心产品功能需求。

## 4. 从截图中提炼出的需求列表

按照明确度和可执行性，截图里的需求可以拆成三类：

### 高明确度需求

1. 支持按艺术家下载。
2. 下载结束后支持重试失败歌曲。
3. 优化文档中的 Docker / wrapper 配置说明，补充 `--platform linux/amd64` 兼容提示。

### 中明确度需求

1. 降低大批量下载时的补漏成本。
2. 减少 wrapper 搭建门槛，尤其是 Apple Silicon 场景。

### 暂不应直接当作需求的内容

1. 网络波动、限流、代理配置问题本身是现象，不是单独功能需求。
2. “并发能力不好提”是技术现状判断，是否要做性能优化还需要结合复现数据。
3. “有 update 第一时间通知我”更接近发布机制或用户沟通，不属于本次功能开发主线。

## 5. 用户真实诉求

用户并不是单纯想多支持一种 URL 类型，真实需求是：

- 想从某个艺术家入口批量整理作品，而不是手动逐专辑导入。
- 希望减少“找链接、补漏、重复操作”的摩擦。
- 希望桌面版的支持范围尽量接近上游 `gamdl` 的能力认知，避免“上游能下，桌面版不行”的落差。

如果把截图里的其他诉求一起看，真实目标可以进一步归纳为：

- 批量下载入口要更完整。
- 出错后的补救路径要更短。
- 环境搭建说明要更不容易踩坑。

## 6. 需求定义

### 核心需求

桌面版支持输入 Apple Music 艺术家链接，并允许用户基于艺术家页面内容发起下载。

### 建议的 MVP 范围

1. 接受 artist URL，不再在前端直接拦截为 unsupported。
2. 进入下载前，让用户选择要下载的艺术家内容类型。
3. 第一版只暴露与音乐下载最相关的几类内容：
   - `Top Songs`
   - `Main Albums`
   - `Singles / EPs`
   - `All Albums`
4. 选择完成后复用现有下载任务队列，不单独设计新下载器。
5. 下载结果继续沿用当前目录模板、封面、歌词、ALAC / wrapper 等既有逻辑。

### 暂不纳入首版

- 在艺术家页内做复杂的多层筛选和搜索。
- 一次性暴露所有上游枚举能力。
- 重新设计独立的“艺术家浏览器”页面。
- 对超大艺术家目录做激进并发优化。

## 7. 交互预期

建议流程：

1. 用户粘贴艺术家链接。
2. 页面识别为 `Artist` 且显示为可支持。
3. 提交时弹出一个简单选择：
   - 下载热门单曲
   - 下载主要专辑
   - 下载单曲与 EP
   - 下载全部专辑
4. 用户确认后，系统把选中的条目展开为现有下载任务。
5. 任务页正常显示进度、失败数和日志。

如果首版想更保守，可以先不做多选，只做“单选内容类型 + 加入任务”。

## 8. 验收标准

满足以下条件可认为该需求完成：

1. 桌面版可以识别并接受 artist URL。
2. 用户可以在 GUI 中完成至少一种艺术家内容类型选择并成功加入下载队列。
3. 选中的歌曲 / 专辑可以走通当前已有下载链路。
4. 非 artist URL 的现有歌曲、专辑、歌单下载行为不回归。
5. README / 界面文案同步更新，明确桌面版新增 artist 支持范围。

## 9. 风险与边界

- 艺术家目录可能很大，展开条目时可能带来更长等待时间。
- 不同艺术家页面的数据完整度可能不一致，首版要优先保证“能解释失败”，而不是静默跳过。
- 如果直接暴露全部 artist 选项，GUI 复杂度会明显上升，MVP 应控制入口数量。
- 如果当前桌面下载服务没有把 `artist_auto_select` 透传到 GUI，需补一层参数映射和任务构建逻辑。

## 10. 关于“是否已有开发计划”

基于当前仓库和截图，能确认的是“这是一个合理且已有底层基础的需求”，但看不到已经公开承诺的开发排期。

更准确的表述应该是：

> 用户已明确提出按艺术家下载的需求；当前仓库底层已有 artist 能力，但桌面版尚未正式开放，适合评估为一个中等成本、可做 MVP 落地的产品化项。
